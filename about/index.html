01 / Open Source / web

The browser client keeps the platform playable.

Vanilla JavaScript owns the shell and the adapters. Rust and WebAssembly own the simulation and frame.

The web repository is the browser client and the static host for the current game package. It deliberately stays small: the DOM, input, HUD, loading, and WebSocket connection live in JavaScript, while the platform runtime is loaded as generated WebAssembly.

The useful mental model is a frame loop with explicit seams. createGame() loads the package, creates the Rust engine and renderer, wires the socket and controls, then advances the engine on every requestAnimationFrame. The browser reads a frame snapshot, updates the HUD, sends local movement, and asks the renderer to draw.

Entry point
src/main.js → src/app/createGame.js
Package host
/games/first-game/, populated from the sibling first-game repo
Runtime boundary
src/engine/wasm.js writes buffers and reads the flat Rust snapshot
Network boundary
src/network/worldSocket.js joins /world/:worldId and publishes changed movement at 12 Hz

The runtime loop

One authoritative local tick.

  1. 01

    Read keyboard, pointer, wheel, or touch input into mutable game state.

  2. 02

    Pass movement, camera deltas, jump, and remote player transforms into Rust.

  3. 03

    Step simulation, follow world transitions, and read the player, pads, agents, and camera snapshot.

  4. 04

    Update DOM presentation and sync the wgpu renderer for the frame.

Developer workflow

Build the seams, not a framework.

  • npm run dev syncs the game package and builds the browser renderer before Vite starts.
  • npm run build:renderer invokes the Rust WASM build and wasm-bindgen output step.
  • Change content in ../first-game; change simulation in ../rust; keep this repo for browser behavior.
  • The browser currently preserves the game-script seam, but does not run the native Luau host in WASM yet.

A browser bug should be traceable to one of three places: input and presentation here, the shared engine, or the package and network contract. That separation is the main feature of this repository.

02 / Open Source / rust

The common runtime is a Rust engine with native and WASM faces.

Simulation, world rules, scripting hooks, snapshots, and primitive rendering live below every client.

The rust repository is the platform-neutral core. It owns the player controller, collision against axis-aligned blocks, camera state, launch-pad countdowns, portals, world transitions, remote-player presentation, and the frame data clients need to draw.

It is compiled three ways from the same crate: as a Rust library for checks, a static library for iOS, and a cdylib wrapped for Android and the browser. The client never needs to know how the engine stores a player or resolves a collision; it sends inputs and consumes the stable ABI.

Core type
src/engine.rs → Engine, with capped remote players and world state
Package model
src/game_package.rs uses serde and camelCase JSON defaults
Rendering
wgpu plus WGSL produces the shared primitive renderer for Metal, Vulkan/GLES, and WebGPU/WebGL
Public seam
src/ffi.rs exposes C-compatible lifecycle calls, buffers, snapshots, and renderer methods

Simulation contract

Input in. Snapshot out.

The engine clamps each step to 50 ms, ticks the game script, smooths camera motion, updates the player and portals, advances remote walk cycles, updates launch pads, and writes a fixed-stride float snapshot. The snapshot contains the local player first, followed by agent records; metadata accessors expose pads, camera, world, and settings state.

Remote players are supplied by a client because the Rust crate does not open sockets. This keeps network policy and identity platform-specific while keeping their rendered representation consistent.

Feature split

Native scripting, portable rendering.

  • Native targets use mlua with vendored Luau; the browser uses the pure-Rust luaur-rt Luau host.
  • WASM uses the same lifecycle host plus browser bindings and wgpu WebGPU/WebGL dependencies instead of native window handles.
  • iOS passes a Metal layer; Android passes an ANativeWindow; the browser passes an HTML canvas.
  • Native and browser Rust engines execute the same lifecycle callbacks through target-specific Luau runtimes.

When changing the engine, verify the three consumers together: the C header and native adapters, the generated WASM binding, and the snapshot layout. A field added to one side is an ABI change, even if the Rust code compiles.

03 / Open Source / ios_app

iOS is a SwiftUI client wrapped around the same engine.

Swift owns lifecycle, touch, identity, and platform presentation. Rust still owns the world.

The ios_app repository is intentionally an adapter rather than a second game implementation. SwiftUI drives loading and screen state, GameViewModel owns the engine lifecycle and 60 Hz tick, and the app sends the same package data and world-socket messages as the browser.

The app can start with a bundled manifest and script, use a cached manifest on the next launch, and refresh declarative content from the web host for a later launch. Executable rules remain bundled; this gives content some update room without downloading arbitrary native behavior.

App state
ContentView.swift → GameViewModel with published loading, frame, world, socket, identity, and moderation state
Package loader
GamePackage.swift decodes the manifest, validates the start world, and manages bundled/cached content
Engine bridge
EngineBridge.swift copies UTF-8 buffers into the C ABI and decodes the float snapshot into Swift value types
Metal surface
RustGameSurface.swift hosts an MTKView; its delegate syncs and draws the Rust renderer

Frame and lifecycle

Swift owns the clock.

A Combine timer ticks the view model at 60 Hz when the game is presented. The view model guards the first tick, clamps the delta, pauses movement while the username editor is open, passes remote players into Rust, steps the engine, follows the active world index, sends movement, and publishes the next frame for SwiftUI.

The MTKViewDelegate owns the platform render cadence. It creates the renderer from the view's CAMetalLayer, resizes it when drawable dimensions change, syncs the engine, draws, and tears it down with the view.

Networking and configuration

Native identity, shared protocol.

  • WorldSocketClient uses URLSessionWebSocketTask, sends movement only when meaningfully changed and no faster than 12 Hz, and reconnects with bounded backoff.
  • Player IDs and usernames persist in UserDefaults; settings-room visibility is sent separately from movement.
  • Debug builds default to localhost; Release builds default to the deployed package and Worker, with environment overrides for LAN testing.
  • The Xcode build phase compiles the sibling Rust crate for the selected simulator or device target and links the static library.

The native integration is intentionally boring at the boundary: copy bytes in, call the engine, decode a known snapshot, and let SwiftUI handle platform UX. That makes iOS-specific work safer to review.

04 / Open Source / android_app

Android brings the same runtime through Compose and JNI.

Kotlin owns state and touch. A small native shim turns an Android surface into the Rust renderer's window.

The android_app repository is the Kotlin/Jetpack Compose port of the iOS client. GameViewModel is the single state holder: it loads and validates the package, creates the native engine, ticks simulation, owns the socket, and exposes a StateFlow for the Compose UI.

Android's platform-specific complexity is concentrated in the build and surface bridge. Gradle builds Rust for the selected ABIs, CMake links a JNI shim, and the shim keeps an ANativeWindow alive long enough for wgpu to create and destroy its surface safely.

App state
game/GameViewModel.kt owns loading, ticking, world transitions, remote players, username, and renderer handles
Compose loop
GameScreen uses LaunchedEffect and withFrameNanos for tick → draw, while UI state stays declarative
Native bridge
nativebridge/NativeEngine.kt declares the small JNI API backed by jni_bridge.c
Build targets
Gradle builds Rust cdylibs for arm64-v8a and x86_64, then packages generated jniLibs

Surface lifetime

Keep the window valid until the renderer is gone.

The Compose screen embeds a native SurfaceView. Surface callbacks create the renderer, forward size changes, and destroy it when the surface disappears. The JNI layer owns the native holder and calls the same engine renderer functions as iOS, while Rust maps the retained window to an Android raw-window handle.

This ordering matters: destroying or replacing the surface before the renderer releases its swapchain can create platform-specific GPU failures. The callback is the lifecycle authority.

Kotlin and networking

One data source, no unnecessary layers.

  • The package loader fetches manifest.json and game.luau over HTTP, parses JSON explicitly, and validates the start world.
  • WorldSocketClient uses OkHttp, persists Android identity, sends the shared movement and username messages, and reconnects with bounded backoff.
  • Gradle properties override package and backend URLs for a device on the dev LAN; Release uses deployed endpoints.
  • The JNI frame read returns Rust's snapshot plus metadata for counts, world, camera, and launch-pad state, which Kotlin decodes into value types.

If an Android rendering issue appears, inspect the full chain—Gradle ABI output, CMake library loading, JNI surface lifetime, and Rust wgpu backend—before changing Compose code.

05 / Open Source / first_game

The first game is a portable package, not a client fork.

JSON describes worlds. Luau supplies game-specific rules. Every client consumes the same package.

The first-game repository is content and rules only. It has no browser, Swift, Kotlin, Rust, or server code. That constraint is what lets the same lobby and session travel across the web, iOS, and Android clients.

manifest.json describes presentation-independent world data: palette, bounds, spawn points, clouds, blocks, portals, launch pads, settings room, avatars, and the runtime world map. The game source lives under first-game/src/; the package builder assembles its Luau modules into the single game.luau entry consumed by the host.

Package schema
manifest.json with startWorld: "lobby", a launch route, and nested worlds
Lobby
Three colored launch pads, shared 8-second countdowns, a settings portal, and a max-player hint of 18
Session
real-game becomes “The Clearing” after the launch and removes the lobby pads
Rules
game.luau exports on_start(api) and on_tick(api, delta); the host API is the portability boundary

Data model

Content stays declarative.

Top-level fields define the lobby. The nested worlds map defines additional scenes with their own palette, grid, spawn, blocks, portals, and signs. Clients synthesize the lobby world from the top-level values and sort runtime world IDs so a world transition can be represented as a stable engine index.

Keep fields compatible with all three loaders: the browser normalizer in web/src/game/, GamePackage.swift, and Android's explicit JSON parser. A schema change is a cross-repository change.

Rules and delivery

Ship data through the web host.

  • web/scripts/sync_first_game.sh builds the source package and writes its manifest, generated script, metadata, and optional assets into public/games/first-game/.
  • iOS and Android bundle the same generated package, then fetch and cache a validated manifest/script pair for the next launch.
  • Native and browser Rust engines execute the same lifecycle callbacks through target-specific Luau runtimes.
  • Platform behavior belongs in the runtime or host API. Keep package rules portable and free of client-specific imports.

This repository is the test of the architecture: if a world or rule needs a platform-specific rewrite, the boundary is in the wrong place—or the package contract needs to become more explicit.

01 / Why build another platform?

Roblox has the network. That is exactly why it is hard to change.

We do not need to win by having everything on day one. We need to be meaningfully better for the first small group that is willing to move.

The goal is not to attack Roblox for existing or pretend that a new platform can instantly replace a world with millions of players, creators, friends, games, and years of accumulated content.

The opportunity is to be more opinionated from the beginning. A new platform does not have to preserve every compromise made to serve kids, teens, adults, developers, brands, investors, and an enormous legacy system all at once.

01

Scale becomes baggage.

Incumbents carry legacy architecture, aging UX decisions, and systems that are difficult to replace without disrupting the ecosystem already built on top of them. A new platform can set better defaults before the compromises harden.

02

Creators become tenants.

When your game only exists inside someone else’s walled garden, the platform owns too much of the relationship. Discovery, economics, identity, and access can feel opaque or arbitrary.

03

Safety gets bolted on.

Moderation controversies and unrestricted stranger contact are not problems that a nicer warning screen can solve. Social architecture, age boundaries, reporting, and appeals need to be part of the system’s design.

04

One product serves everyone.

A platform that must satisfy children, parents, professional developers, casual players, brands, and investors will always make tradeoffs. cubacadabra can choose a clearer center of gravity: creators first, with families in mind.

02 / The opportunity

The answer is not a prettier clone.

Safety gets a family’s attention. A better relationship with the people who build the worlds gives them a reason to stay.

“Roblox but safer” is an important starting point, but safety is primarily a reason for parents to approve. The stronger idea is a platform where several advantages reinforce each other.

Kids get fun worlds and friends. Parents get substantially safer social architecture. Creators get tools, ownership, economics, and a relationship that treats them like developers building an ecosystem—not tenants renting space in someone else’s mall.

A

Trust and safety by design

Tighter age separation, no unrestricted adult-to-child contact, transparent moderation metrics, strong community reporting, safety research, and real appeals are future design goals—not features we claim to have today.

B

A better creator deal

We want simpler revenue share, clearer economics, fewer arbitrary platform taxes, easier cash-out, and transparent discovery. The creator should understand how the platform works and what they can expect from it.

C

A better developer experience

Modern rendering, native scripting and development workflows, proper package management, reproducible builds, local servers, sane debugging, and documented formats and APIs can make building feel like development again.

D

More room to build

Native clients, better performance, richer physics and networking, portable assets and worlds, and fewer historical constraints could give creators a higher technical ceiling.

03 / Open by design

Your cubacadabra game should not be trapped inside cubacadabra.

Creator-first should describe the architecture, not just the marketing.

Openness is not just a philosophy here. It can be part of the competitive strategy. If creators can inspect the engine, understand networking, use documented file formats and scripting APIs, and submit fixes, the relationship changes from “trust our black box” to “help shape the tools you depend on.”

If the runtime and formats are open, a creator also has more confidence that their work will remain usable if the company ever changes direction. That is a real answer to platform risk: the work does not simply disappear behind a proprietary executable.

Open where openness helps

  • Rust engine and common runtime
  • Web, iOS, and Android clients
  • SDKs, Luau bindings, and creator tools
  • World and asset formats
  • Protocol definitions and local servers
  • Sample games and public documentation

Private where secrecy protects

  • Production safety models and abuse heuristics
  • Anti-cheat detection and ban-evasion signals
  • Fraud rules, payment risk, and private operations
  • Moderator and law-enforcement tooling
  • Credentials, secrets, and infrastructure details

Open anything where openness benefits creators, interoperability, trust, or contribution. Keep private anything where secrecy materially raises the cost of abuse.

04 / The hard part

The source code is not the moat.

Openness makes the foundation more useful. Trust, people, and great worlds are what make a platform worth choosing.

“Even though Roblox has everybody, this is so much better for what I do that I’m moving.”

Roblox’s network effect is real. An open renderer or a better local server does not create millions of players overnight. The moat we eventually have to earn is players, creators, friends, games, a world catalog, trust, moderation operations, discovery data, and an economy that people actually want to participate in.

Someone could fork the code and call it CubeBlox. They would not automatically get cubacadabra’s players, popular games, creator relationships, reputation, or safety operation. If the code is good enough that people want to fork it, that is evidence that it became useful.

05 / Three constituencies

Different reasons to choose the same world.

The best outcome is not asking one audience to compromise for another. It is giving each audience a reason to prefer the same place.

01

Kids and players

Fun worlds, expressive play, friends, and reasons to come back.

02

Parents

A social environment designed to be substantially safer and easier to understand.

03

Creators

A platform that treats the people making the worlds much better.

06 / Where we are now

Early enough to change the rules.

The project is small enough to be honest, ambitious, and still able to make foundational choices carefully.

Today, cubacadabra is still a tiny shared world in progress: a small lobby, an open baseplate, and the beginning of a common runtime. The platform described above is future work. The economics, safety architecture, creator tooling, portable formats, mobile clients, and broader ecosystem are not done.

That is also the reason to make the direction explicit now. The choices made early can determine whether creators feel like participants or tenants, whether families can understand the social system, and whether the code becomes a wall or a foundation.
